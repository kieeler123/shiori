# Shiori 개발 기록 --- 2026-10-09

## 리스트형 정리

### 오늘의 목표

-   React 클라이언트에서 직접 수행하던 글 CRUD를 Fastify API로
    단계적으로 이전한다.
-   기존 Supabase 인증, 데이터, UI를 유지하면서 실제 화면에서 동작을
    검증한다.
-   휴지통과 첨부파일 삭제의 책임 범위를 확인한다.

### 구현·확인한 작업

1.  **글 목록 조회(Read)**: `GET /api/logs`를 사용해 페이지네이션과
    정렬을 확인했다.
2.  **글 상세 조회(Read)**: `GET /api/logs/:id`를 도입하고, 존재하지
    않는 글은 404로 처리한다.
3.  **글 작성(Create)**: `POST /api/logs`를 통해 실제 글 생성과 201
    응답을 확인했다. 입력 검증과 중복 처리, 뷰에서 보이지 않는 글의 반환
    형태도 점검했다.
4.  **글 수정(Update)**: `PATCH /api/logs/:id`로 수정하고 200 응답을
    확인했다. `unknown[]`와 `ReferenceItem[]` 사이의 타입 문제를
    살펴보며 Zod 스키마의 필요성을 확인했다.
5.  **휴지통 이동(Delete/soft delete)**: `DELETE /api/logs/:id`에서 204
    응답을 확인했다. 이 단계에서는 로컬 첨부파일이 유지된다.
6.  **휴지통 목록**: `GET /api/logs/trash`에서 200 응답을 확인했다.
7.  **영구 삭제**: `DELETE /api/logs/:id/permanent`에서 첨부파일 없는
    글의 204 응답을 확인했다.
8.  **첨부파일이 있는 글의 삭제**: 기존 React·Supabase 경로와 브라우저
    파일 삭제 기능을 유지했다. 휴지통에서 완전 삭제할 때 Windows 폴더의
    파일이 사라지는 것을 확인했다.
9.  **로컬 첨부파일 구조 조사**: File System Access API와
    `FileSystemDirectoryHandle`로 사용자가 연결한 폴더에 저장하며,
    `attachments/YYYY/MM/DD/UUID.ext` 형태의 경로를 사용함을 확인했다.
10. **외부 파일 삭제 위험 검토**: Windows 탐색기에서 직접 파일을
    삭제하는 것을 현 구조에서 완전히 막을 수 없음을 확인했다.

### 오늘 확인한 HTTP 결과

  작업                         메서드와 경로                      확인
  ---------------------------- ---------------------------------- ------
  목록                         `GET /api/logs`                    200
  작성                         `POST /api/logs`                   201
  수정                         `PATCH /api/logs/:id`              200
  휴지통 이동                  `DELETE /api/logs/:id`             204
  휴지통 목록                  `GET /api/logs/trash`              200
  첨부파일 없는 글 영구 삭제   `DELETE /api/logs/:id/permanent`   204

### 아직 완료되지 않은 부분

-   모든 프런트엔드의 Supabase 직접 DB 접근 제거.
-   운영 환경에서 사용할 Fastify 서버 배포 및 API 주소 구성.
-   `dbCreate()`의 비로컬 분기에 남아 있는 Supabase 직접 저장 로직 복원
    또는 운영 API 전환.
-   로컬 첨부파일과 Supabase Storage의 안전한 서버 측 삭제 통합.
-   공유 첨부파일 참조 검사, 삭제 실패 재시도, 파일 누락 감지 및 백업.
-   Windows 로컬 PostgreSQL을 주 저장소로 이전하고 데이터·권한·백업을
    검증.

### 다음 개발 순서

1.  현재 작동하는 상태를 Git에 안전하게 기록한다.
2.  API 호출 규약과 에러 처리를 통일한다.
3.  프런트엔드의 DB 직접 접근을 기능별로 제거한다.
4.  첨부파일 관리와 영구 삭제를 안전하게 분리·개선한다.
5.  Fastify와 PostgreSQL을 Windows에서 실행하고 데이터 이전을 검증한다.
6.  클라이언트는 API 계약만 알고, 서버는 DB와 파일 저장소를 관리하는
    구조로 정리한다.

**팁:** 오늘 확인한 성공 응답과 아직 검증하지 않은 기능을 구분해
기록하면 다음 작업에서 회귀 오류를 줄일 수 있다.
