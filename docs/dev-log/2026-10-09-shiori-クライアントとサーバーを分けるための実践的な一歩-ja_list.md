# Shiori 開発記録 --- 2026年10月9日

## リスト形式

### 今日の目標

-   React から直接実行していた記事の CRUD を Fastify API
    へ段階的に移行する。
-   既存の Supabase 認証、データ、UI を維持しながら実画面で検証する。
-   ゴミ箱と添付ファイルの削除責任を整理する。

### 実装・確認した内容

1.  **一覧取得**：`GET /api/logs`。ページングと並び替えを確認。
2.  **詳細取得**：`GET /api/logs/:id`。対象が存在しない場合は 404。
3.  **新規作成**：`POST /api/logs`。実際の記事作成と 201
    を確認。入力検証、重複、ビューの表示条件も検討。
4.  **更新**：`PATCH /api/logs/:id`。200 を確認。`unknown[]` と
    `ReferenceItem[]` の型不一致を調査。
5.  **ゴミ箱への移動**：`DELETE /api/logs/:id`。204
    を確認。この時点ではローカルファイルを残す。
6.  **ゴミ箱一覧**：`GET /api/logs/trash`。200 を確認。
7.  **完全削除**：添付ファイルのない記事で
    `DELETE /api/logs/:id/permanent` の 204 を確認。
8.  **添付ファイル付き記事**：既存の React・Supabase
    経由の削除処理を維持。ゴミ箱から完全削除すると Windows
    上のファイルが消えることを確認。
9.  **ローカル保存の調査**：File System Access API
    を利用し、`attachments/YYYY/MM/DD/UUID.ext` の相対パスに保存。
10. **外部からの削除リスク**：Windows
    エクスプローラーによる直接削除を現在の構造だけで完全には防げないことを確認。

### 確認できた HTTP 応答

  操作                 API                                応答
  -------------------- ---------------------------------- ------
  一覧                 `GET /api/logs`                    200
  作成                 `POST /api/logs`                   201
  更新                 `PATCH /api/logs/:id`              200
  ゴミ箱へ移動         `DELETE /api/logs/:id`             204
  ゴミ箱一覧           `GET /api/logs/trash`              200
  添付なしの完全削除   `DELETE /api/logs/:id/permanent`   204

### 未完了の課題

-   フロントエンドに残る Supabase への直接 DB アクセスの解消。
-   本番環境向け Fastify の配置と API 接続設定。
-   `dbCreate()` の非ローカル分岐における保存処理の復元、または本番 API
    への移行。
-   添付ファイルの安全な削除統合、共有参照チェック、失敗時の再試行。
-   ファイルの欠損検知、復元、世代管理バックアップ。
-   Windows 上の PostgreSQL をメインの保存先とする移行と検証。
