# Shiori 개발 일지 --- 2026년 10월 9일

## 클라이언트와 서버를 분리하기 위한 첫 번째 실전 검증

오늘 Shiori 개발의 중심 과제는 글 관리 기능을 React 클라이언트에서
Fastify 서버로 조금씩 옮기는 일이었다. 목표는 단순히 HTTP 요청을
추가하는 것이 아니었다. 기존 UI와 Supabase 인증, 저장된 글을 유지하면서
앞으로 클라이언트와 서버가 각자의 역할에 집중할 수 있는 기반을 만드는
것이었다.

먼저 글 목록과 상세 조회를 Fastify API로 연결했다. 목록은 페이지네이션과
정렬 조건을 전달하며 가져오도록 구성했다. 글 작성에서는
`POST /api/logs`의 201 응답을, 수정에서는 `PATCH /api/logs/:id`의 200
응답을 실제 화면에서 확인했다. 글 작성 과정에서는 입력 검증과 중복 확인,
조회용 뷰의 필터 때문에 저장한 글이 바로 표시되지 않을 수 있다는 점도
살펴봤다. 수정 기능을 옮기는 동안에는 `unknown[]`와 `ReferenceItem[]`의
타입 불일치가 나타나 입력 스키마의 역할을 다시 확인했다.

삭제는 단순한 CRUD보다 더 섬세한 문제였다. Shiori에서 일반 삭제는 즉시
데이터를 없애는 작업이 아니라 휴지통으로 이동하는 soft delete다.
`DELETE /api/logs/:id`의 204 응답을 확인했고, 휴지통 목록은
`GET /api/logs/trash`에서 200 응답을 확인했다. 첨부파일이 없는 글을 위한
영구 삭제 API에서도 204 응답을 확인했다.

특히 의미 있었던 것은 로컬 첨부파일의 동작을 실제 Windows 폴더에서
검증한 일이다. Shiori는 브라우저의 File System Access API로 사용자가
연결한 폴더에 파일을 저장한다. 테스트 결과 글을 휴지통으로 보낼 때
파일은 그대로 남았고, 휴지통에서 완전 삭제할 때 파일이 사라졌다. 이
동작은 복구 가능성을 지키면서 영구 삭제 시 정리하는 현재 설계의 의도와
맞는다. 다만 첨부파일이 있는 글의 완전 삭제는 아직 기존 React·Supabase
경로를 사용하므로, 모든 삭제 책임이 Fastify로 옮겨진 것은 아니다.

여기서 새로운 질문도 생겼다. 사용자가 Windows 탐색기에서 첨부파일을 직접
삭제하면 어떻게 될까? 현재 브라우저 기반 폴더 접근 방식은 그 행동을
완전히 막지 못한다. 따라서 파일 존재 여부 검사, 누락 경고, 다시
연결하기, 버전 관리형 백업 같은 보호 장치가 필요하다. 파일 삭제 후 DB
삭제가 실패하거나 여러 글이 하나의 파일을 참조하는 문제도 앞으로
해결해야 한다.

오늘의 성과는 모든 것을 완성한 데 있지 않다. 글 CRUD와 휴지통 API의 주요
흐름을 실제 요청으로 검증했고, 로컬 첨부파일이 언제 삭제되는지
확인했으며, 남은 경계를 구체적으로 파악했다는 데 있다. 프런트엔드에는
아직 Supabase 직접 호출이 남아 있고 Fastify 역시 Supabase PostgreSQL을
사용한다. Windows 로컬 PostgreSQL을 주 저장소로 전환하는 일도 아직 시작
단계다.

다음에는 현재 상태를 Git에 보존하고, 클라이언트의 DB 직접 접근을
기능별로 줄여 나갈 계획이다. 그 후 첨부파일 관리와 실패 복구를 보강하고,
로컬 PostgreSQL과 서버 관리형 파일 저장소를 차근차근 도입하고자 한다.
최종적으로는 클라이언트가 서버의 내부 저장 방식을 알 필요 없이 API만
사용하고, 서버가 데이터와 파일을 책임지는 Shiori를 만들고 싶다.

**오늘의 팁:** 큰 구조 변경은 한 번에 끝내기보다 작동하는 경계를 하나씩
확인하는 편이 안전하다. 오늘 검증한 API 응답과 파일 삭제 시점을 다음
개발의 기준점으로 삼자.
