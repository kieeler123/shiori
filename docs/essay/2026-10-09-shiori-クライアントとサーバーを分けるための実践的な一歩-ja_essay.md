# Shiori 開発日誌 --- 2026年10月9日

## クライアントとサーバーを分けるための実践的な一歩

今日の Shiori 開発では、React クライアントに集中していた記事管理の処理を
Fastify サーバーへ少しずつ移すことに取り組んだ。目的は HTTP
通信を増やすことではない。既存の UI、Supabase
認証、蓄積してきた記事を守りながら、将来的にクライアントとサーバーの役割を明確にするための土台を作ることだった。

一覧取得と詳細取得を API
化し、一覧ではページングと並び替えを扱えるようにした。新規作成は
`POST /api/logs` の 201、更新は `PATCH /api/logs/:id` の 200
を実画面で確認した。作成時の入力検証や重複確認、データベースのビューに表示されない記事の扱いも見直した。更新処理では
`unknown[]` と `ReferenceItem[]` の型不一致が現れ、API
の入力境界で構造を検証する重要性を再認識した。

削除処理では、通常の削除と完全削除の違いが特に重要だった。Shiori
の通常削除は記事をゴミ箱へ移す soft delete
であり、`DELETE /api/logs/:id` の 204 を確認した。ゴミ箱一覧の
`GET /api/logs/trash` では 200、添付ファイルのない記事の完全削除 API
では 204 を確認した。

今日の印象的な検証は、Windows のローカル添付ファイルだった。Shiori
はブラウザーの File System Access API
を使い、ユーザーが接続したフォルダーにファイルを保存する。実際に確認すると、記事をゴミ箱へ移した段階ではファイルが残り、ゴミ箱から完全削除した際にファイルが消えた。復元可能な期間はファイルを保持するという設計に合致している。ただし、添付ファイル付き記事の完全削除は現在も既存の
React・Supabase の処理経路を利用しており、すべてが Fastify
に移行したわけではない。

さらに、Windows
エクスプローラーからファイルを直接消してしまう場合の問題も考えた。現状のブラウザー経由の保存方式では、そうした削除を完全に防ぐことは難しい。ファイルの欠損検知、再接続、世代管理バックアップ、共有参照の確認、削除失敗時の再試行が今後の重要な課題になる。

今日の成果は、すべての分離作業を完了したことではない。CRUD
とゴミ箱の主要な API
を実際の応答で確かめ、ローカルファイルの削除タイミングを検証し、残された責任の境界を明確にできたことにある。フロントエンドにはまだ
Supabase への直接アクセスが残り、Fastify も Supabase PostgreSQL
を利用している。Windows のローカル PostgreSQL
をメインの保存先にする作業はこれからだ。

次回は動作中の状態を Git に残し、機能ごとにクライアントの DB
直接アクセスを減らしていく。続いて添付ファイル管理と失敗時の復旧を強化し、Windows
上の PostgreSQL
とサーバー管理型のファイル保存領域を段階的に導入したい。最終的には、クライアントがサーバー内部の保存方法を知らず、API
だけを通して利用できる Shiori を目指す。

**今日のヒント：**
大きな設計変更は一度に終わらせるより、動作する境界を一つずつ検証する方が安全だ。
