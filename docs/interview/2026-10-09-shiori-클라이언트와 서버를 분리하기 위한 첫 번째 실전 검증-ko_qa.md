# Shiori 개발 기록 --- 2026-10-09

## 질문과 답변

### Q1. 오늘 무엇을 하려고 했나?

**A.** 기존 React·Supabase 중심의 글 관리 기능을 Fastify API로
단계적으로 옮기고, 실제 UI에서 CRUD 동작을 확인하려 했다.

**팁:** 기능 이전에서는 기존 화면과 데이터의 동작을 유지하는 것이
우선이다.

### Q2. CRUD는 어디까지 확인했나?

**A.** 글 작성(`POST /api/logs`, 201), 조회(`GET /api/logs`, 200),
수정(`PATCH /api/logs/:id`, 200), 휴지통 이동(`DELETE /api/logs/:id`,
204)을 확인했다. 상세 조회 API도 구현했다.

**팁:** HTTP 응답뿐 아니라 화면에 표시되는 값과 DB 상태도 함께 확인한다.

### Q3. 휴지통 기능은 어떻게 작동하나?

**A.** 일반 삭제는 글을 휴지통으로 옮기는 soft delete다. 휴지통 목록은
`GET /api/logs/trash`로 200 응답을 확인했고, 첨부파일 없는 글의 영구
삭제 API는 204 응답을 확인했다.

**팁:** 휴지통 이동과 영구 삭제는 서로 다른 작업으로 취급한다.

### Q4. 로컬 첨부파일은 언제 삭제되나?

**A.** 실제 테스트에서 휴지통으로 이동할 때는 파일이 유지됐고,
휴지통에서 완전 삭제할 때 Windows 폴더의 파일이 사라졌다.

**팁:** 휴지통 이동 직후 파일이 남아 있어야 복구가 가능하다.

### Q5. 로컬 첨부파일은 어디에 저장되나?

**A.** 브라우저 File System Access API로 사용자가 연결한 폴더에
저장된다. 상대 경로는 `attachments/YYYY/MM/DD/UUID.ext` 형태다. 삭제 시
`FileSystemDirectoryHandle.removeEntry()`를 사용한다.

**팁:** 브라우저가 접근할 수 있는 폴더와 Fastify 서버가 접근할 수 있는
폴더는 동일하다고 가정하지 않는다.

### Q6. 탐색기에서 파일을 직접 지우지 못하게 할 수 있나?

**A.** 현 구조에서 Shiori만 삭제할 수 있도록 완전히 제한하기는 어렵다.
대신 파일 존재 여부 감지, 복원, 버전 관리형 백업이 실용적이다. 서버 전용
저장소와 Windows 권한 분리는 장기 과제다.

**팁:** 삭제 방지와 삭제 후 복구를 별도로 설계한다.

### Q7. 타입 오류는 무엇이었나?

**A.** `validateContentBlocks()`가 `ReferenceItem[]`를 요구하는데 일부
업데이트 입력이 `unknown[]`로 정의되어 있었다. Zod 스키마로 참조 항목의
`id`를 검증하고 타입을 맞추는 방향을 검토했다.

**팁:** 검증 없이 `as ReferenceItem[]`로 단언하기보다 입력 경계에서
구조를 검증한다.

### Q8. 클라이언트와 서버는 완전히 분리됐나?

**A.** 아직 아니다. 일부 기능은 여전히 프런트엔드에서 Supabase를 직접
호출한다. 또한 Fastify의 저장소도 현재는 Supabase PostgreSQL이다.

**팁:** 완전 분리는 프런트엔드가 DB 구현을 모르고 API 계약만 사용하는
상태를 목표로 한다.

### Q9. Windows 로컬이 주 저장소가 됐나?

**A.** 아니다. 로컬 첨부파일 기능은 존재하지만 주 데이터베이스를 Windows
PostgreSQL로 전환하지는 않았다.

**팁:** 이전 전에는 백업, 데이터 정합성, 인증과 접근 권한을 먼저
검증한다.

### Q10. 다음에는 무엇부터 하나?

**A.** Git 체크포인트를 만든 뒤 남은 Supabase 직접 접근을 정리하고, 영구
삭제·첨부파일 참조 검사·백업을 개선한 후 로컬 PostgreSQL 이전을
준비한다.

**팁:** 기능을 한 번에 바꾸지 말고 API별로 이전·테스트·확정한다.
