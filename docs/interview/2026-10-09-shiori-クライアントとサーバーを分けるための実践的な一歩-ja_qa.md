# Shiori 開発記録 --- 2026年10月9日

## 質問と回答

### Q1. 今日の目的は？

**A.** React・Supabase に依存していた記事 CRUD を Fastify API
へ段階的に移し、既存 UI で動作を確かめること。

**ヒント：** 移行中は既存の画面とデータの互換性を優先する。

### Q2. CRUD はどこまで確認できた？

**A.** 作成 `POST /api/logs`（201）、一覧 `GET /api/logs`（200）、更新
`PATCH /api/logs/:id`（200）、ゴミ箱への移動
`DELETE /api/logs/:id`（204）を確認した。詳細取得 API も実装した。

**ヒント：** HTTP ステータスだけでなく、画面表示と DB の状態も照合する。

### Q3. ゴミ箱はどう動く？

**A.** 通常の削除は soft delete。ゴミ箱一覧 `GET /api/logs/trash` は
200、添付ファイルのない記事の完全削除 API は 204 を確認した。

**ヒント：** ゴミ箱への移動と完全削除は別の操作として扱う。

### Q4. ローカル添付ファイルはいつ消える？

**A.**
実際のテストでは、ゴミ箱へ移した時点では残り、ゴミ箱から完全削除した際に
Windows フォルダーから消えた。

**ヒント：** 復元可能な間は添付ファイルを保持する。

### Q5. ローカルファイルはどこにある？

**A.** File System Access API
でユーザーが接続したフォルダーに保存する。相対パスは
`attachments/YYYY/MM/DD/UUID.ext`。削除には `removeEntry()` を使う。

**ヒント：** ブラウザーと Fastify
が同じフォルダーへアクセスできるとは限らない。

### Q6. エクスプローラーからの直接削除を防げる？

**A.**
現行構造では完全な防止は難しい。ファイルの存在確認、再接続、履歴付きバックアップが現実的。専用サーバー保存領域と権限分離は将来の課題。

**ヒント：** 削除の防止と削除後の復元を別々に考える。

### Q7. 型エラーの原因は？

**A.** `validateContentBlocks()` が `ReferenceItem[]`
を要求する一方、更新入力の一部が `unknown[]` だった。Zod で参照項目の
`id` を検証し、型を揃える方針を検討した。

**ヒント：** 型アサーションより入力境界での検証を優先する。

### Q8. クライアントとサーバーは完全に分離された？

**A.** まだ。フロントエンドには Supabase の直接呼び出しが残り、Fastify
の DB も現状は Supabase PostgreSQL である。

**ヒント：** 最終的にはクライアントが API 契約だけを知る構成を目指す。

### Q9. Windows のローカル DB がメインになった？

**A.** まだ。ローカル添付ファイルの仕組みはあるが、PostgreSQL
のメイン保存先は移していない。

**ヒント：** データ移行前にバックアップと権限、整合性を確認する。

### Q10. 次に何をする？

**A.** Git で現状を保存し、残りの DB
直接アクセスを整理する。その後、添付ファイル削除の安全性とバックアップを改善し、ローカル
PostgreSQL 移行へ進む。

**ヒント：** API ごとに移行、検証、確定を繰り返す。
